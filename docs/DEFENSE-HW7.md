## 0. Что показывать (сценарий демонстрации, 5 минут)

Обязательно на **production-сборке**: `npm run build && npm run preview` → http://localhost:4173
(в dev-режиме воркера нет — это осознанное решение, см. вопрос 9).

1. **DevTools → Application → Manifest** — валиден, иконки на месте, кнопка установки в адресной строке.
2. **Application → Service Workers** — один воркер, `activated and is running`.
3. **Application → Cache Storage** — три кэша: `fleetdesk-precache-3.0.0-…`, `fleetdesk-api-v1`,
   `fleetdesk-assets-v1`. Открыть пару машин → в API-кэше появляются `vehicles/veh-xxxx.json`.
4. **Network** — у `api/fleet.json` в колонке Size написано `(ServiceWorker)`, в Response Headers
   видны `x-served-from: sw-cache` и `x-cached-at`.
5. **Network → Offline**, перезагрузить: приложение стартует, список на месте, в шапке «Offline»,
   под шапкой «Offline — showing data saved at …». Открыть машину, которую ещё не открывали — она
   открывается (fallback на каталог). Перейти на `#/dashboard`, который ещё не открывали — грузится,
   потому что чанк в precache.
6. Вернуть сеть — индикатор и баннер исчезают, данные обновляются в фоне.
7. Мобильная версия: DevTools → iPhone SE (375) и 320 px — бургер-меню, нет горизонтальной прокрутки.

## 2. Вероятные вопросы

**1. Почему данные вынесены в статические JSON — это же не «настоящий» API?**
Курс явно разрешает симулированный API (HW4: «simulated asynchronous API using Promises, random
delays, errors and `localStorage`»; HW5: «fake api responses count if they behave like api»).
Но Service Worker перехватывает только HTTP: `setTimeout` + `localStorage` он не видит. Поэтому
данные стали настоящими файлами, а симулированный API остался сверху — задержки 400–900 мс,
`AbortSignal`, валидация, `ApiError` со статусами. Это также выполняет требование HW5 «use real API
responses, not hardcoded data».

**2. Почему две стратегии именно такие?**
Каталог меняется между деплоями и должен быть доступен офлайн → stale-while-revalidate: мгновенный
ответ из кэша + фоновое обновление. Хешированные ассеты по своему URL не меняются никогда →
cache-first, самый дешёвый вариант. Навигации — отдельный случай (вопрос 4).

**3. Почему `index.html` отдаётся cache-first, а не network-first?**
`index.html` ссылается на хешированные чанки. Если отдать свежий `index.html` поверх старого
precache, страница запросит чанки, которых в кэше нет, — белый экран. Оболочка и её ассеты обязаны
переезжать одним куском, и двигает их только новая версия воркера.

**4. Как офлайн работает роутинг, если у вас hash-router?**
Фрагмент URL (`#/vehicles/veh-0007`) вообще не отправляется на сервер: воркер всегда видит навигацию
на один и тот же документ. Поэтому «ранее посещённые страницы работают офлайн» сводится к одному
закэшированному `index.html` + чанкам. Это же причина, почему `cache.match(request)` для навигации не
сработал бы: запрос идёт на `/`, а в precache лежит ключ `.../index.html` — матчим по `SHELL_URL`.

**5. Зачем тогда `offline.html`, если есть маршрут `#/offline`?**
Воркер не может отправить браузер на hash-маршрут. `offline.html` — это ответ на ситуацию, когда нет
сети и нет самой оболочки (например, Safari вычистил storage через 7 дней). Он самодостаточен: ни
скриптов, ни стилей из бандла. В обычной жизни пользователь видит `#/offline`.

**6. Как пользователь получает новую версию?**
Новый воркер устанавливается и **ждёт** — `skipWaiting()` в `install` не вызывается. Приложение
узнаёт об этом по `updatefound` → `statechange` (`registerSW.js`) и показывает тост. Кнопка шлёт
`SKIP_WAITING`, воркер активируется, срабатывает `controllerchange`, страница перезагружается один
раз (модульный флаг `reloading` + проверка `hadController`, чтобы первая установка не перезагружала).
Ничего чистить руками не нужно: в `activate` удаляется только старый precache.

**7. Почему API- и asset-кэши не версионируются по сборке?**
Иначе каждое обновление приложения стирало бы офлайн-данные пользователя. У них версия схемы
(`-v1`), и её поднимают руками только при изменении формата.

**8. Как ограничен рост кэша?**
`trimCache` после каждой записи: `cache.keys()` отдаёт записи в порядке вставки, а `put` при
ревалидации переносит запись в конец — получается FIFO, который ведёт себя как LRU для всего, чем
реально пользуются (80 записей API, 60 ассетов). Плюс `sweepExpired` по возрасту (7 и 30 дней) при
активации. Просроченная запись при чтении не отвергается: устаревшие данные лучше пустого экрана.

**9. Почему в dev-режиме воркера нет?**
Precache-манифеста до сборки не существует (Vite отдаёт несобранные модули из `/src`), а кэширующий
воркер воюет с HMR и начинает отдавать устаревшие модули — это выглядит как необъяснимые баги.
Поэтому `registerServiceWorker()` работает только при `import.meta.env.PROD`, а `/sw.js` в dev отдаёт
воркер, который удаляет сам себя и кэши `fleetdesk-*`.

**10. Чем `navigator.onLine` не устроил?**
Он означает лишь «поднят сетевой интерфейс»: captive portal в кафе, упавший VPN и мёртвый аплинк
рапортуют `true`. Доверяем только отрицанию; положительный ответ доказываем запросом `ping.txt`
(`no-store`, таймаут 3 с), который воркер намеренно не перехватывает. Плюс бесплатный и самый точный
сигнал — реальный трафик приложения: каждый успех и каждый сетевой сбой в `http.js` обновляют
состояние. В офлайне — повтор с backoff 5→60 с, в онлайне опроса нет вообще.

**11. Почему аутентификация не кэшируется?**
Правило 3 в `fetch`: запросы к `googleapis.com`, `firebaseapp.com`, `gstatic.com` и т. п.
возвращаются **без** `respondWith`. Это не только «не кэшируем», но и сохраняет credentials и связь
popup-окна с открывшей его страницей — если прогнать такой запрос через `fetch` внутри воркера, вход
через Google ломается с `auth/network-request-failed`. Плюс правило 1: любые не-GET запросы не
трогаются вообще.

**12. Как пользователь понимает, что видит кэш?**
Воркер при ответе из кэша добавляет `X-Served-From: sw-cache` и `X-Cached-At`. `http.js` их читает,
кладёт в стор, `useCacheStatus` отдаёт в React. В списке — пометка «· saved copy at 14:32», в шапке —
баннер, который появляется офлайн или если копии больше 5 минут (иначе он висел бы всегда: SWR почти
всегда отвечает из кэша, и это нормально).

**13. Что именно сломалось бы без `ignoreVary: true`?**
Vite ставит `crossorigin` на теги скриптов и стилей, поэтому документ запрашивает их в CORS-режиме с
заголовком `Origin`. Запрос воркера при `addAll` его не отправлял. Хостинг отдаёт ассеты с
`Vary: Origin` — и обычное сопоставление по Vary промахивается ровно на главном чанке и CSS.
Симптом: онлайн всё работает, офлайн — белый экран. Поймано тестом, а не в проде.

**14. Почему ответы ассетов не пересобираются ради заголовков?**
`new Response(...)` теряет `response.url`. JS-модуль без URL ответа не может разрешить собственные
относительные импорты (`./index-xxx.js`), и ленивые страницы падают с «failed to fetch dynamically
imported module». Пересобираются только JSON-ответы API — их читает приложение, а не загрузчик
модулей.

**15. Что работает офлайн, а что нет?**
Работает: оболочка, все посещённые и непосещённые страницы (чанки в precache), список, дашборд,
карточки машин (включая те, чей файл не запрашивался — fallback на каталог), создание машины, смена
статуса, удаление (overlay в `localStorage`). Не работает: вход и выход — им нужен Firebase.

**16. Как проверялось, что это всё правда работает?**
Headless-Chromium прогоняет сценарий: установка воркера, наполнение кэшей, остановка сервера (не
эмуляция, а реально убитый origin), перезагрузка офлайн, открытие незакэшированной машины и
непосещённой страницы, возврат сети, 320 px и альбомная ориентация, размеры всех целей нажатия,
полный цикл обновления версии. Два бага нашлись именно так: пауза запросов React Query в офлайне и
промах precache из-за `Vary`.
