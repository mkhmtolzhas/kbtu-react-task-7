**Главная идея структуры — правило зависимостей (сверху вниз, никогда наоборот):**

```
  pages / components          ← только JSX и обработчики событий
          ↓ вызывают
  hooks (useAuth, use*Query)  ← состояние и кэш
          ↓ вызывают
  services / api              ← единственные, кто трогает сеть, localStorage и Firebase SDK
```

Отсюда прямо следует требование задания «не обращаться к `localStorage` и не делать запросы
внутри компонентов»: `localStorage` есть только в `src/api/storage.js`, `sessionStorage` —
только в `useSessionState.js`, Firebase SDK — только в `firebase.js` и `authService.js`.

**Почему именно такие файлы, а не иначе:**

| Вопрос | Ответ |
| --- | --- |
| Почему `firebase.js` отдельно от `authService.js`? | `firebase.js` — инициализация (что за проект, откуда ключи), `authService.js` — действия. Поменять провайдера аутентификации = переписать один сервис, не трогая инициализацию. |
| Почему `AuthContext.js` и `AuthProvider.jsx` — разные файлы? | Правило `react-refresh/only-export-components`: если файл экспортирует и компонент, и что-то ещё, ломается hot reload. Линтер в проекте включён на `--max-warnings 0`, так что это не стиль, а требование сборки. |
| Почему `useAuth` — третий файл? | По той же причине: хук — не компонент. |
| Почему `queries/` отдельно от `hooks/`? | В `queries/` — конфигурация кэша без React (ключи и настройки можно импортировать откуда угодно, в том числе из тестов), в `hooks/` — React-обвязка над ней. |
| Почему `utils/` отдельно от `hooks/`? | В `utils/` — чистые функции без состояния и без React; их можно вызывать и из API-слоя (например, `validateVehicle` используют и форма, и «сервер»). |

```
                  │   └─ VehicleDetails key={id}      useVehicleQuery
                  │       ├─ StatusControl            useUpdateStatusMutation + useAuth
                  │       ├─ DeleteVehicleControl     useDeleteVehicleMutation + useAuth
                  │       └─ SimilarVehicles          useSimilarVehiclesQuery
                  ├─ NewVehiclePage         #/vehicles/new  ← ProtectedRoute
                  │   └─ VehicleForm                  useCreateVehicleMutation
                  ├─ LoginPage / SignupPage #/login, #/signup
                  └─ ProfilePage            #/profile       ← ProtectedRoute
```

**Почему `QueryClientProvider` снаружи, а `AuthProvider` внутри?** Внутренний провайдер видит
внешний, но не наоборот. `AuthProvider` сейчас запросов не делает, но если завтра ему понадобится
`useQuery` (например, тянуть роль пользователя) — он уже внутри кэша и ничего двигать не придётся.
Обратный порядок такой возможности бы не дал.

**Почему `queryClient` создаётся через `useState(createQueryClient)`, а не `new QueryClient()` в теле?**
Тело компонента выполняется на каждый ре-рендер — новый клиент означал бы пустой кэш каждый раз.
`useState` с функцией-инициализатором вызывает её ровно один раз (`App.jsx:51`).

## 3. Переменные окружения

- `import.meta.env` читается **только** в `src/firebase.js:28–35`.
- Vite отдаёт в браузер только переменные с префиксом `VITE_` — остальные не попадают в бандл.
- Env-файлы читаются **при старте** dev-сервера: после правки `.env.local` нужен рестарт.
- `.env.local` в `.gitignore`, в репозитории лежит `.env.example` с плейсхолдерами.
- `firebase.js:22–23` считает недостающие переменные; если хоть одной нет — SDK **не инициализируется**,
  `auth === null`, в шапке появляется баннер, а остальная часть приложения продолжает работать.

> **Вопрос, который почти наверняка зададут:** «Если ключи всё равно видны в бандле, зачем `.env`?»
> Конфиг Firebase — не секрет, он **идентифицирует** проект, а не даёт доступ. Защита — это
> authorized domains и правила безопасности на стороне Firebase. `.env` нужен для другого:
> не хардкодить конфиг в коде и подставлять разные проекты в разных окружениях (dev / preview /
> production на Vercel). Настоящие секреты так хранить нельзя — они живут только на сервере.

## 4. Аутентификация: полный жизненный цикл

**Запуск приложения**
1. `AuthProvider` стартует со `status: 'loading'` (`AuthProvider.jsx:24`).
2. В `useEffect` подписывается на `observeAuthState` → `onAuthStateChanged` (`AuthProvider.jsx:26–45`).
3. Firebase восстанавливает сессию из `localStorage` и вызывает колбэк: `user` + `status: 'ready'`.
4. Cleanup эффекта возвращает `unsubscribe` — отписка при размонтировании.

**Вход**
1. Страница вызывает `signIn(email, password)` из `useAuth()`.
2. `authService` ждёт `persistenceReady` (`firebase.js:40–42`) и зовёт `signInWithEmailAndPassword`.
3. Состояние **не пишется напрямую** — его обновит `onAuthStateChanged`. Это и есть единственный
   источник истины: вход в соседней вкладке приходит сюда тем же путём.
4. Страница делает `navigate(from)`, где `from` — путь, с которого пользователя увели (`LoginPage.jsx:24`).

**Выход** — `signOut()` → снова срабатывает подписка → `user: null` → `ProtectedRoute` уводит на `/login`.

**Ошибки** — всё, что выходит из `authService`, это `AuthError` с полями `code`, `message`, `field`
(`authService.js:14`). Словарь `MESSAGES` (`authService.js:25`) переводит коды Firebase в человеческие
фразы, `FIELD_BY_CODE` указывает, у какого поля формы показать сообщение.

**Почему в `ProtectedRoute` спиннер, а не сразу редирект?** Пока Firebase восстанавливает сессию,
пользователь ещё не «анонимный» — состояние неизвестно. Без различения `loading` и «не вошёл»
залогиненного выбрасывало бы на `/login` при каждой перезагрузке страницы (`ProtectedRoute.jsx:15`).

## 5. Кэш: полный жизненный цикл запроса

**Ключи** (`queries/queryKeys.js`) — параметры запроса лежат **внутри** ключа:

```
['vehicles', 'list', { search, status, class, district, sortBy, sortDir, page, pageSize }]
['vehicles', 'detail', 'veh-0007']
['vehicles', 'stats']
['vehicles', 'similar', { vehicleClass, district }]
```

Поэтому каждая комбинация фильтров — своя запись кэша, и возврат к уже открытому фильтру или
странице происходит мгновенно, без запроса.

**Что происходит при `useVehiclesQuery({...})`:**
1. React Query считает хэш ключа и смотрит в кэш.
2. Есть свежая запись (моложе `staleTime`) → отдаёт её, запроса нет.
3. Есть устаревшая → отдаёт её **сразу** и параллельно перезапрашивает (stale-while-revalidate).
4. Записи нет → `isPending: true`, вызывается `queryFn` с `signal`.
5. Ключ изменился (новый фильтр) → предыдущий запрос **прерывается** через `AbortSignal`.

**Настройки** (`queries/queryClient.js:19–27`):

| Параметр | Значение | Смысл |
| --- | --- | --- |
| `staleTime` | 60 000 мс (счётчики — 30 000) | сколько ответ считается свежим |
| `gcTime` | 5 мин | сколько неиспользуемая запись живёт в памяти до удаления |
| `refetchOnWindowFocus` / `refetchOnReconnect` | включены | фоновая ревалидация **только устаревших** записей |
| `retry` | 1 повтор, только для 5xx | 404/409/422 — окончательный ответ, повторять бессмысленно |

**Инвалидация** (`hooks/useVehicleQueries.js`):

| Операция | Что делает с кэшем |
| --- | --- |
| создание (`:91–95`) | `setQueryData` для новой карточки + инвалидация списков, счётчиков, «похожих» |
| смена статуса (`:107–112`) | `cancelQueries` до мутации, затем `setQueryData` + те же инвалидации |
| удаление (`:124–127`) | `removeQueries` для карточки (сущности больше нет) + те же инвалидации |

**Три защиты от «старый ответ затёр новый»:**
1. `signal` прерывает запрос с устаревшим ключом (`:29, :37, :46, :73`).
2. Ответ пишется в запись **своего** ключа, а не в ту, которую сейчас смотрит пользователь.
3. `cancelQueries` перед мутацией статуса: летящий GET иначе приземлится после PATCH и вернёт старый статус.

Плюс `placeholderData: keepPreviousData` (`:30`) — при смене страницы старые результаты остаются
на экране приглушёнными с пометкой «Updating…» вместо мигания спиннером.

## 7. Вероятные вопросы и короткие ответы

**Про аутентификацию**

- *Где хранится сессия?* — `browserLocalPersistence` → Firebase кладёт токен в `localStorage`
  (ключ `firebase:authUser:…`). Переживает перезагрузку и перезапуск браузера. Альтернативы:
  `browserSessionPersistence` (на вкладку) и `inMemoryPersistence` (до перезагрузки).
- *Когда срабатывает `onAuthStateChanged`?* — сразу после восстановления сессии при старте, затем при
  каждом входе/выходе, в том числе выполненном в другой вкладке.
- *Почему Google через popup, а не redirect?* — popup не теряет состояние страницы и проще в SPA;
  `signInWithRedirect` пришлось бы дополнять обработкой `getRedirectResult` после возврата.
- *Что будет, если открыть `/profile` по прямой ссылке без входа?* — `ProtectedRoute` отдаст
  `<Navigate to="/login" state={{ from }} replace />`; после входа вернёт обратно на `/profile`.
  `replace` — чтобы кнопка «назад» не возвращала на защищённую страницу.
- *Почему смена статуса не редиректит на логин, а просто заблокирована?* — пользователь читает
  карточку; выбрасывать его со страницы за клик по действию — плохой UX. Показываем подсказку со ссылкой.
- *Как бы вы ограничили права по-настоящему?* — на клиенте это только UI; реальная проверка должна
  быть на сервере (Firebase Security Rules / проверка ID-токена на бэкенде). Здесь «сервер» —
  симуляция в браузере, поэтому ограничение честно остаётся интерфейсным.

**Про кэш**

- *Чем `staleTime` отличается от `gcTime`?* — `staleTime`: сколько данные считаются свежими
  (не перезапрашиваются). `gcTime`: сколько запись живёт в памяти **после того, как её перестали
  использовать**. Разные оси: актуальность и время жизни.
- *`invalidateQueries` сразу делает запросы?* — нет. Помечает записи устаревшими и перезапрашивает
  только **активные** (у которых есть смонтированный компонент). Остальные обновятся при следующем открытии.
- *Чем `invalidateQueries` отличается от `removeQueries`?* — первое оставляет данные (их ещё покажут,
  пока грузится свежие), второе удаляет запись целиком. Для удалённой машины нужно именно второе:
  показывать её данные больше нельзя.
- *Зачем `setQueryData`, если всё равно инвалидируете?* — ответ мутации уже содержит свежую сущность:
  кладём её в кэш и экономим лишний GET. Инвалидация нужна для **других** записей (списков, счётчиков),
  которых ответ мутации не касается.
- *Почему не сделали оптимистичное обновление?* — «сервер» валидирует смену статуса и может отказать
  (нельзя сдать машину с топливом ниже 15 %). Откатывать интерфейс после отказа было бы хуже, чем
  подождать 0,5 секунды. `onMutate` используется только для отмены конкурирующего GET.
- *Что будет, если убрать `signal` из `queryFn`?* — запросы перестанут прерываться: при быстром
  перещёлкивании фильтров старый ответ может прийти позже нового. Для карточки это вернуло бы
  данные другой машины на экран.
- *Почему своего кэша не писали?* — задание разрешало оба варианта; TanStack Query даёт ключи,
  `staleTime`, инвалидацию, отмену и `keepPreviousData` из коробки — писать и отлаживать это
  самому значило бы повторить библиотеку хуже.

**Про структуру и прочее**

- *Почему hash-роутер?* — работает на любом статическом хостинге без rewrite-правил. Из-за этого в
  `vercel.json` не нужен (и даже вреден) catch-all rewrite: вместе с относительными путями
  `base: './'` он ломал бы ассеты на вложенных URL.
- *Почему 180 машин лежат в `localStorage`?* — настоящего бэкенда нет, а требование курса — список
  из 100+ записей, переживающий перезагрузку.
- *Как проверить обработку ошибок?* — `?simulateError=1` в URL: все запросы падают, видны состояния
  error и кнопка Retry. `?simulateError=0.3` — падает примерно треть.

## 9. Демонстрация за 3 минуты

1. **Без входа**: список, фильтр, пагинация. Открыть машину → вернуться → **спиннера нет** (кэш).
2. Нажать «Add vehicle» → **редирект на `/login`** (защищённый маршрут).
3. Войти → вернуло ровно на форму добавления (`state.from`). В навбаре — профиль и Log out.
4. `/profile`: email, UID, метод входа. **Перезагрузить страницу** — сессия на месте.
5. Добавить машину → открылась её карточка → вернуться в список: **счётчик и список уже знают** о ней
   (инвалидация), хотя страницу никто не обновлял.
6. Сменить статус → счётчики в шапке списка меняются на −1/+1.
7. Выйти → на карточке действия заблокированы с подсказкой «Log in to …», `/profile` снова уводит на логин.
8. Код: `firebase.js` (откуда ключи) → `AuthProvider` (один эффект) → `useVehicleQueries.js` (ключи и инвалидация).
